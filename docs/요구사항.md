# 사례비서 요구사항 문서 (Claude Code 전달용)

> **Claude Code에게:** 이 문서는 "사례비서" 개발의 기준이다. 한 번에 전부 만들지 말고 **8장의 단계를 하나씩** 진행한다. 각 단계가 끝나면 통과 기준을 직접 확인한 결과를 보고하고 **멈춘 뒤 사용자 확인을 기다린다.** 1장의 절대 규칙은 어떤 경우에도 어기지 않는다. 문서와 다르게 해야 할 이유가 생기면 바꾸기 전에 먼저 묻는다.

---

## 1. 절대 규칙

1. **원본 형식 그대로 돌려준다.** 기관이 준 양식 파일(HWP, HWPX, DOCX 등)은 받은 형식 그대로 돌려준다. HWP를 HWPX로 바꿔서 돌려주는 것처럼 형식을 바꾸지 않는다. 서식, 칸, 병합, 배치, 글꼴, 표 구조를 바꾸지 않고, 채울 칸의 내용만 바꾼다.
2. **없는 정보를 만들지 않는다.** 사례 기록에 없는 내용은 쓰지 않는다. 채울 근거가 없는 칸은 비워 두고 `[확인 필요]`로 표시한다. 채운 칸마다 근거가 된 기록(날짜, 기록 ID)을 남긴다.
3. **판단은 담당자가 한다.** 선정 여부, 욕구 수준 점수, 우선순위, 대상자 동의, 서명·직인, 사례관리 여력 같은 칸은 자동으로 채우거나 체크하지 않는다.
4. **개인정보는 기관 PC에 둔다.** 사례 기록과 채운 서류는 사용자 PC에만 저장한다. AI로 보낼 때는 이름, 주민등록번호, 연락처, 주소, 사례 카드에 등록된 가족·관계인 이름을 기호로 바꿔 보내고, 돌아온 결과에 PC에서 원래 값을 다시 넣는다.
5. **실제 개인정보로 시험하지 않는다.** 모든 테스트는 가상 사례로 한다.
6. **표준 양식 파일을 제품에 포함해 배포하지 않는다.** 서울시 사회복지관 표준 양식은 협회 저작물이라 테스트용으로만 쓴다. 양식은 기관이 직접 올리는 것이 기본이다(4.6).

---

## 2. 제품 정의

**사례비서:** 사례관리 담당자가 상담 기록을 쌓아 두면, 기관마다 다른 양식 파일에 채울 수 있는 칸은 원본 서식 그대로 채우고, 비어 있는 칸은 다음 방문 때 물을 질문으로 알려 주며, 지역 자원과 가계도·생태도까지 같은 기록에서 만들어 주는 업무 도우미.

- **사용자:** 지자체(통합사례관리사, 통합돌봄 담당자, 읍면동 맞춤형복지팀), 사회복지관 등의 사례관리 담당자
- **사용 환경:** 기관 PC(Windows), Chrome 또는 Edge, 한글 프로그램
- **AI가 하는 일:** 이미 적힌 기록을 양식에 맞게 **옮기고 정리**하는 것. 새 사실을 알아내거나 판단하지 않는다.

### 2.1 사용 흐름

| 단계 | 담당자 | 사례비서 |
|---|---|---|
| 기록 쌓기 | 상담·방문·전화 메모를 붙여 넣음(나중에 녹음 추가) | 기록을 날짜순으로 저장하고, 기록에서 사실을 뽑아 사례 카드 항목 후보로 제시 → 담당자가 확인해야 반영 |
| 양식 채우기 | 기관 양식 파일을 올림 | 칸을 분석해 채울 칸은 채우고, 빈칸 목록과 다음 방문 질문을 만들고, 원본 형식 파일로 돌려줌 |
| 자원 찾기 | 버튼을 누름 | 사례 카드 조건으로 내장 자원 데이터에서 후보, 근거, 확인할 질문을 제시 |
| 가계도·생태도 | 관계 표를 확인·수정 | 그림을 그리고 이미지로 내보냄 |
| 기록 초안 | 메모를 넣음 | 과정기록지, 사례회의록 초안 |

## 3. 사례 카드 (공통 데이터)

### 3.1 원칙
- 사례 카드는 **한 번 입력하는 서식이 아니라 계속 쌓이는 기록**이다.
- 모든 항목은 값, 근거 기록 ID, 확인 여부(담당자가 확인함 / AI 후보)를 가진다.
- 항목 구성은 **서울시 사회복지관 사례관리 표준 매뉴얼(2025.3 개정)의 인테이크 기록지·사정기록지** 항목을 기준으로 한다.

### 3.2 구조 (초안, 개발 중 조정 가능)

```
Case {
  id, createdAt, updatedAt
  records: Record[]              // 상담·방문·전화·회의 기록 (원문 보관)
  general: {                     // 일반사항
    protectionType,              // 보호구분: 맞춤형급여(생계/의료/주거/교육), 차상위, 일반저소득, 기타
    householdType,               // 1인가구, 노인부부, 부모자녀, 한부모, 조손, 다문화, 기타
    housing: { type, ownership, condition },
    disability: { has, type, degree },
    longTermCare: { grade },
    referralPath, interviewType
  }
  people: Person[]               // 대상자와 가족·관계인 (가계도와 공유)
  unions: Union[]                // 혼인·동거 관계 (6장)
  needs: {                       // 14개 욕구영역
    clothing, food, dailyLiving, health, psychological, employment,
    economy, housing, educationDevelopment, carePrimary,
    familySocialRelations, familyFunction, safety, rightsLegal
  }                              // 각 영역: 서술, 세부 사실 목록, 근거 기록 ID
                                 // 욕구수준·우선순위 칸은 담당자 입력 전용
  services: Service[]            // 이용 중이거나 연계한 서비스
  ecomap: EcoLink[]              // 외부 체계와의 관계 (6장)
  plan, evaluations, closure     // 계획·평가·종결 (담당자 입력 중심, AI는 초안)
}

Field<T> { value: T, sourceRecordIds: string[], status: 'confirmed' | 'suggested' }
Record { id, date, type: '상담'|'방문'|'전화'|'회의'|'기타', rawText, author }
```

### 3.3 기록에서 항목 뽑기
- 새 기록이 들어오면 AI가 사실을 뽑아 **바뀐 항목만** 제시한다(예: "경제: 월세 2개월 체납 — 11/16 방문 기록").
- 담당자가 승인한 것만 반영한다. 기존 값과 충돌하면 둘 다 보여 주고 담당자가 고른다.

## 4. 양식 채우기 엔진 (핵심 기능)

### 4.1 처리 순서
1. **형식 판별:** HWP(5.x), HWPX, DOCX. PDF는 4.6 참고.
2. **구조 읽기:** 표, 셀, 병합(colspan/rowspan), 셀 안의 문단, 글자 모양, 체크박스 기호(□ 등)를 읽는다.
3. **칸 역할 분류:** 각 셀을 다음 중 하나로 분류한다.
   - `label`: 항목명("성명", "주소")
   - `input`: 값을 쓸 빈칸
   - `checkbox_group`: □ 선택지 묶음
   - `guide`: 안내 문구가 들어 있고 지우고 써야 하는 칸(예: "※ 인테이크 욕구내용은…")
   - `judgment`: 담당자 판단 칸(선정 여부, 욕구수준 점수, 우선순위, 사례관리 여력)
   - `signature`: 서명, 직인, 동의
   - `personal`: 인적·식별 정보(성명, 주민번호, 연락처, 주소). 사례 카드에 담당자가 입력한 값만 쓰고 AI는 관여하지 않는다
   - `fixed`: 바꾸면 안 되는 고정 문구
4. **매핑:** 칸과 사례 카드 항목을 연결한다. AI는 표 구조(라벨 위치, 머리글 행·열)를 보고 제안하고, 코드는 그 제안을 검증한다(존재하지 않는 항목에 연결 금지). 한 번 확인한 매핑은 **양식별 템플릿으로 저장**해 다음부터 재사용한다.
5. **값 만들기:**
   - 서술 칸: AI가 사례 카드와 기록만 근거로 작성한다. 칸 폭과 줄 수에 맞춰 분량을 조절한다.
   - 체크박스: 규칙으로 처리한다(사례 카드 값이 있으면 해당 □만 바꿈). 체크 기호는 설정 가능(■, ☑, V 등. 기본값 ■).
   - 근거가 없으면 비우고 `[확인 필요]` 목록에 추가한다.
6. **원본에 쓰기:** 원본 파일의 해당 셀 내용만 교체한다.
7. **검증:** 9.2의 검사를 자동으로 돌린다.
8. **결과:** 채운 파일(원본과 같은 형식), 칸 지도(채움 / 확인 필요 / 담당자 입력), 다음 방문 질문 목록.

### 4.2 이미 확인된 문제와 해결 요구
2026.11.18에 서울 표준 인테이크 기록지로 시험한 결과, 아래 문제가 있었다. 반드시 해결한다.

| 문제 | 해결 요구 |
|---|---|
| 안내 문구 칸에 쓰면 안내 문구의 글자 모양(회색 기울임)이 남음 | `guide` 칸에 쓸 때는 글자 모양을 같은 셀 또는 양식 본문의 일반 글자 모양으로 바꾼다 |
| HWP에서 줄 수가 줄면 빈 줄이 남음(사용한 도구가 셀 안 문단 삭제 미지원) | 남는 문단을 삭제한다. 필요하면 HWP 문단·글자 모양을 직접 다루는 라이브러리를 함께 쓴다 |
| 좁은 칸에서 줄바꿈이 어색함(면접일시, 비고) | 칸 폭에 맞춰 문장을 줄이거나, 칸 폭 대비 글자 수 한도를 계산해 AI에게 전달한다 |
| 원래 굵은 밑줄 서식이 있는 칸에 쓴 내용이 굵은 밑줄로 나옴 | `input` 칸의 기존 서식이 안내용 서식인지 판단해 일반 서식으로 쓴다 |
| 내용이 늘면 표가 다음 쪽으로 밀림 | 막을 수는 없지만, 쪽 수 변화를 결과 보고에 표시한다 |
| 특수 기호(가구유형의 선택 기호 등) | 손대지 않는 칸은 원본 바이트를 그대로 유지한다 |

### 4.3 쓸 수 있는 도구 (검토 대상)
- **kordoc** (MIT, Node.js): HWP·HWPX·DOCX·PDF 읽기, 표 구조를 HTML 표로 추출, 서식 보존 수정(patch), HWP 직접 수정 가능. 2026.11.18 시험에서 HWP 원본에 23곳을 서식 보존 상태로 반영하는 데 성공. 셀 안 문단 삭제는 HWP에서 미지원.
- **hwplib / hwpxlib** (Java): HWP 문단, 글자 모양, 줄 배치 정보를 직접 다룰 수 있음. 사업계획서 양식 채우기에 실제로 사용함.
- DOCX: 서식 보존 수정이 가능한 라이브러리를 고른다.
- 도구를 바꾸거나 추가할 때는 라이선스를 확인해 보고한다.

### 4.4 다음 방문 질문
- `[확인 필요]` 칸마다 담당자가 대상자에게 물을 수 있는 질문 1개를 만든다(예: "부채: 현재 갚고 있는 빚이 있는지, 금액과 상환 방식은 어떤지 확인해 주세요").
- 질문은 양식의 항목 설명과 사례 카드의 기존 정보를 바탕으로 만들고, 이미 아는 내용을 다시 묻지 않는다.

### 4.5 화면: 양식 칸 지도
- 양식 미리보기와 칸 목록을 나란히 보여 준다.
- 칸마다 배지를 단다: 채움(근거 보기) / 확인 필요(질문 보기) / 담당자 입력 / 판단 칸.
- 담당자는 채운 내용을 고치거나 비울 수 있고, 고친 내용으로 다시 파일을 만든다.

### 4.6 양식 확보 방식
- **기본: 기관이 자기 양식을 올린다.** 제품에는 양식 파일을 넣지 않고, 양식을 읽고 채우는 엔진만 넣는다. 서울 표준 양식을 쓰는 기관은 이미 가지고 있는 파일을 올린다.
- **양식 템플릿 재사용:** 처음 올린 양식의 칸 분석·매핑 결과를 양식 템플릿으로 저장해 다음부터 바로 채운다. 템플릿은 그 기관 PC 안에만 저장한다. 같은 양식의 새 버전이 올라오면 바뀐 칸을 찾아 알려 준다.
- **자체 기본 서식:** 양식이 없는 기관을 위해 사례비서가 직접 만든 기본 서식(과정기록지, 사례회의록 등)을 제공한다. 기존 표준 양식을 베끼지 않고 새로 만든다.
- **협약 시 탑재(나중):** 서울시사회복지관협회 등 양식 저작권자의 허락을 받으면, 그 양식과 템플릿을 제품에 미리 넣을 수 있게 구조를 열어 둔다(양식 묶음을 별도 데이터로 관리). 허락 전에는 넣지 않는다.

### 4.7 PDF 양식 (2차)
- 입력 필드가 있는 PDF는 필드를 채운다.
- 필드가 없는 PDF는 1차에서 "채울 칸 목록과 텍스트"만 제공하고, 파일에 직접 쓰는 기능은 별도로 결정한다.

## 5. 지역자원 찾기

### 5.1 데이터
- **전국 기본:** 공공데이터포털 '대한민국 공공서비스(혜택) 정보' API, 한국사회보장정보원 사회복지시설 정보 API
- **시범 지역(1곳, 사용자가 정함):** 지자체 복지서비스 데이터, 지자체·기관 자원 안내책자(PDF)
- **안내책자 처리:** AI로 항목을 뽑아 표로 만든 뒤 **사람이 검수**한 것만 넣는다. 책자별 이용 조건을 기록한다.
- API 키는 사용자가 발급해 설정 파일에 넣는다. 키를 코드나 저장소에 넣지 않는다.

### 5.2 자원 구조
```
Resource { id, name, provider, region, targetConditions, benefit, howToApply,
           contact, source, sourceUrl, lastVerifiedAt, informal: false }
```
- 후원자 개인 같은 비공식 자원은 데이터화하지 않는다.

### 5.3 찾는 방식
1. 규칙으로 걸러 낸다(지역, 연령, 보호구분, 가구유형, 장애, 장기요양 등급).
2. AI는 **걸러진 목록 안에서만** 순서를 정하고 근거를 단다. 목록에 없는 자원을 만들지 않는다(코드로 검증).
3. 결과마다 근거(사례 카드의 어떤 사실과 맞는지), 기관에 확인할 질문, 출처, 최종 확인일을 표시한다.
4. 담당자가 기관에 확인한 결과(대상 맞음/아님, 메모)를 저장해 다음 검색에 반영한다.

## 6. 가계도·생태도

### 6.1 가계도 데이터 (혼인 단위)
```
Person { id, name, sex: 'M'|'F'|'unknown', birthYear, deathYear?, isClient,
         isPregnancy?, isMiscarriage?, occupation?, note? }
Union  { id, partnerA, partnerB, type: 'marriage'|'cohabitation',
         status: 'married'|'separated'|'divorced'|'widowed'|'ended',
         startYear?, endYear?, children: [{ personId, kind: 'bio'|'adopted'|'foster', twin?: { groupId, identical } }] }
Household { memberIds }  // 동거 가구선
```
- 한 사람이 여러 혼인·동거 관계를 가질 수 있다.
- 자녀는 **혼인 단위에 붙인다.** 한쪽 부모만의 자녀(의붓자녀)는 그 부모와 전 배우자의 Union에 붙이고, 전 배우자를 모르면 '알 수 없음' 인물을 만든다.

### 6.2 그리기 요구
- AI는 기록에서 관계 표를 만드는 데까지만 한다. 그림은 코드가 그린다.
- 표준 기호: 남 □, 여 ○, 사망 ×(이름을 가리지 않게), 결혼 실선, 동거 점선, 별거 /, 이혼 //, 일란성·이란성 쌍둥이, 태아, 유산, 중심인물 이중선, 동거 가구선, 사망연도·나이 표시.
- **겹침 없는 자동 배치.** 경쟁 도구 시험에서 나온 문제를 반드시 통과한다.
  - 재혼 배우자가 첫 배우자와 같은 자리에 겹치지 않을 것
  - 형제를 추가해도 다른 인물과 겹치지 않을 것
  - 동거인을 추가해도 기존 혼인의 이혼 표시와 자녀 연결이 바뀌지 않을 것
  - 의붓자녀가 공동 자녀처럼 그려지지 않을 것
- 담당자가 위치를 끌어 옮길 수 있고, 옮긴 위치를 저장한다.
- PNG와 SVG로 내보낸다. 사정기록지의 가계도 칸에 이미지로 넣는 기능은 2차.

### 6.3 생태도
- 중심에 대상자 또는 가구 원(가족 묶음)을 두고, 외부 체계를 배치한다.
- 사람과 기관은 다른 모양으로 그린다.
- 관계: 강한 관계, 보통, 약한 관계, 소원, 갈등(스트레스). 에너지 방향: 양방향, 나감, 들어옴.
- 대상이 많으면 원을 여러 겹으로 배치해 겹치지 않게 한다. 긴 이름은 줄바꿈하거나 원 밖에 표시한다.
- 가계도와 같은 사례 카드의 인물을 쓴다(두 번 입력하지 않음).

## 7. 개인정보와 보안

- **저장:** 사례 데이터는 사용자 PC에만 저장한다. 서버에 저장하지 않는다. 가능하면 저장 데이터를 암호화하고 잠금 비밀번호를 둔다.
- **AI 전송 전 가림:**
  - 사례 카드의 인물 목록(대상자, 가족, 관계인)에 있는 이름은 모두 기호로 바꾼다(`[대상자1]`, `[가족2]` 등). 성을 뺀 이름이나 호칭도 포함한다.
  - 주민등록번호, 전화번호, 이메일, 상세 주소는 패턴으로 바꾼다.
  - 보내기 전에 바뀐 결과를 확인 화면(모달)으로 보여 주고, 걸러지지 않았을 수 있는 정보(기관명, 희귀 질환명, 구체적 날짜·장소)를 경고한다.
  - 돌아온 결과의 기호를 PC에서 원래 값으로 되돌린다.
- **AI 제공자:** 호출 부분을 하나의 모듈로 분리해 제공자를 바꿀 수 있게 한다. 입력 데이터를 학습에 쓰지 않는 조건의 API만 쓴다.
- **로그:** 오류 로그에 사례 내용이나 개인정보를 남기지 않는다.
- **공공 도입 대비:** 기관 내부망 설치형으로 바꿀 수 있는 구조를 유지한다.

## 9. 테스트 자료와 검사

### 9.1 가상 사례 10개 (사용자와 함께 작성)

- 짧은 메모 / 긴 서술 / 맞춤법이 엉망인 메모 / 정보가 많이 빠진 메모
- 여러 번에 걸친 기록(1차~3차 방문)

- 파일이 오류 없이 열림(가능한 판독기로 확인)
- 원본과 결과의 렌더 이미지 비교 결과를 함께 보고
